# Touch, clipboard, and the line field: evidence-led direction

Current interaction contract for touch, clipboard and the line field; device-specific touch and clipboard gates remain. This supplements [browser-behaviors.md](browser-behaviors.md); a mockup or desktop probe does not prove real touch or clipboard behavior. Evidence: [terminal-interaction-sources.md](terminal-interaction-sources.md), [terminal-interaction-probe.md](terminal-interaction-probe.md), and the pinned-source study [terminal-selection-source-research.md](terminal-selection-source-research.md).

## Decisions supported now

### One gesture owner, not separate competing click handlers

A tap on the terminal resolves to one action in `touchControl.ts`, in the app and in phone Safari alike:
- In an application that asked for a supported mouse-reporting mode (alternate-screen status alone is insufficient), the tap is a remote mouse click and raises nothing.
- Otherwise, if the terminal's input does not hold the keyboard, the tap raises it: it focuses the terminal input (from the line box too, which gives typing back to the terminal). The focus is made in the tap's own `touchend`, since iOS shows the keyboard only for a focus made in the gesture.
- With the terminal's input already holding the keyboard, a tap on an OSC 133 input row moves the prompt cursor, and anywhere else does nothing.
- With a selection or mark up, a tap elsewhere only closes it and raises nothing (below).

Only the key row's toggle lowers the keyboard. Desktop click-to-focus is unchanged.

**Selection on the phone is the page's own in a browser, and muxen's mark in the app.** On touch the row list draws the rows as page text, tmux's history included, and the browser scrolls it, so in a browser iOS's long press selects a word with its own handles and menu: muxen draws nothing of the selection and its recognizer never sees a long press. The terminal's own cursor is a CSS outline while the terminal input is not focused. Movement before a long press is scrolling; a touch within 22 px of the selected text is the system's (its handles reach past the glyphs) and never reaches the recognizer. Scrolling does not close it: moving the view redraws nothing, and in phone Safari a drag of a handle to the list's top or bottom edge autoscrolls it (iOS's own). New output closes it only when the cap drops its rows, or a frame rewrites them and their text is gone from the screen (J7). A tap elsewhere, a resize, a font change, a snapshot or an input switch closes it. The rows' colours are CSS variables, so a theme change redraws nothing. A range dragged out of the terminal is cut to the rows. Copy goes through the copy event, which joins soft wraps across the rows; Paste is the line box's, not the terminal's. Copying never clicks the application or pastes back into it, and a touch sends no mouse event (the surface takes none for 800 ms after one). Double-tap word selection is off. **In the app, with the keyboard up or down,** the hold is muxen's (`selection/mark.ts`), one selection in both states: iOS's own selection would drop the keyboard, and with it down it felt slow: the recognizer's hold marks the word under the finger (`caretRangeFromPoint`, `Intl.Segmenter`) and draws it as boxes in the list's scroller (`RowRanges.rectsOf`, the placement the handles use, redrawn on the same events), which is not a DOM selection, so focus stays. The finger, still down, extends the mark from that word, in either direction; two drawn handles (selection-look.md in the work item) adjust it, each dragged by the vector from the finger to its text point, so it doesn't jump on grab; a mark never collapses (an end stops one character short of the other). A drag hides iOS's menu and the lift brings it back (`editMenu`, Copy through native `copy`, Paste through `menuPaste`); a tap inside the mark toggles the menu, a tap elsewhere clears the mark and does nothing else (it raises no keyboard), a scroll only hides the menu (a tap inside brings it back), the mark autoscrolls the list while a handle or the holding finger is within 40 px of its top or bottom, and rows redrawing under it follow J7 (output never pauses). The mark's range goes through the same `RowRanges.textOf` join as the DOM selection's Copy. `TerminalView` picks one `Selection` when it is built (the mark where the platform has `editMenu`, the DOM selection otherwise), so the two never coexist and every rule about "the selection" (J7, dismissal, Copy, a touch that begins on it) is written once. A `touchcancel` while the finger holds the mark (a system gesture took the touch) ends it as a lift does: the mark stays with its handles and menu, since nobody dismissed it. A second finger down during the hold ends it as a cancel does: the mark stays with its handles and menu. A reset (a tab switch, a snapshot) or the app going to the background drops the mark first, so no menu shows for it. A light haptic (`key`) marks the word. The handles are children of the list's scroller, so they ride its native scroll; the scroller clips, so a start knob that would lie above the scroller's visible top hangs below its line, as the end knob does. The page's own boxes hold the keyboard in the app, so nothing keeps WebKit's long press from selecting the rows: where the mark is the selection (`data-marking` on the surface) the rows are `user-select: none` and `-webkit-touch-callout: none`, and iOS's selection can't start beside the mark. `caretRangeFromPoint` finds nothing in `user-select: none` text, so `Mark.caretAt` makes the scroller selectable just for the call. In a browser (no `editMenu`, so no mark) the hold stays WebKit's. This terminal-selection gesture has no spacebar-trackpad mapping. Do not send remote mouse-down on initial touch: send tap press/release only after the gesture resolves as a tap.

The browser adapter must declare pan ownership with touch-action before gestures and handle pointer cancellation, not fight the browser with blanket preventDefault. Coordinate conversion uses actual terminal-cell metrics, visual viewport offsets, the list's rows, and pane identity. Do not derive cell coordinates from guessed font size. Native/web adapters feed the same semantic interaction intents, with one focus owner per environment.

Whether iOS starts its selection from a long press on the rows, and where it sends `touchcancel`, cannot be validated from desktop synthetic events; the phone checks it. Double-tap word select is off on touch: it would send an unwanted first click.

### Copy logical terminal text, not screen-shaped HTML

Soft wraps are not line breaks. Explicit hard breaks and blank lines remain; partial selections include only their endpoints. Indentation must survive. Terminal grid copy is not a byte-for-byte reconstruction of the program's original file (tabs may already have been expanded by terminal rendering).

On the phone the selectable representation is the rows themselves: Copy reads the page's selection and joins the rows by `isWrapped`, with no snapshot. Do not scrape canvas pixels, insert BR at every displayed row, or use an unrelated innerText serializer. Render untrusted terminal content as text, not HTML.

On the phone the selection is on live rows that stay put: a row is redrawn only when its text changes. When a frame redraws rows under the selection (J7), the selection keeps its text, not its rows: if the selected rows' whole text, as a contiguous block, is unchanged in place (a style-only change included), it stays. If that block now sits at other rows of the same screen, in exactly one place, the selection moves there with the same columns (a full-screen app such as Claude Code or OpenCode repaints older text a few rows up or down when a status line grows). Otherwise it closes: the text changed, it appears in more than one place, or it left the screen (an alternate screen has no history to follow it into). A repaint that reaches muxen split across frames shows the text gone in between, and closes. Output never pauses. The rule is one function in `selection/rowRanges.ts`, applied to the one `Selection`, so the mark and the page's selection obey it alike; when it moves the mark, native's menu hides (a tap inside brings it back). The list holds at most 10,000 rows and creates no second always-running terminal emulator or unbounded history for inactive panes.

**Wrap prerequisite resolved by L3:** the daemon now pairs physical `-N -T` rows with `-J` logical rows in the same command group, then replays only unambiguous continuations into xterm's `isWrapped` state. History chunks carry a separate bitmap and the history driver joins those rows for copy. This fixes the data boundary after reconnect, snapshot, and history fetch; it does not implement the mobile selection UI or prove real-device clipboard behavior. Full-width rows are not evidence of wrapping: a hard newline can occur at the exact same column.

### Paste uses one path and the receiving app's mode

Clipboard text and the line field's Return use the existing paste request → private temp file → tmux load-buffer/paste-buffer -p route. Do not convert each newline into an independent key event and do not add a trailing Enter to a clipboard paste (the line field's Return adds exactly one Enter after its paste). Avoid double-wrapping bracketed paste in both browser and tmux. Pane-side mode is authoritative; reconstructed frontend mode may be incomplete after snapshot.

Observed on tmux 3.4: LF becomes CR inside the terminal paste stream; bracketed markers are present only when the pane app enabled them. Clipboard trailing newline remains a trailing newline. Consequently, embedded newlines can execute commands when bracketed paste is absent or mishandled; “no extra Enter” is not a safety guarantee.

Use real user paste/copy events and text/plain. A user-driven Copy action may call clipboard write within the gesture, with explicit failure feedback; do not await a slow server read and assume Safari will retain activation. Have bounded selection data ready before Copy. Synthetic ClipboardEvents do not establish clipboard permissions or actual paste behavior. Image paste stays the existing upload/path route, separate from plain text.

### The dock: line field, key row and one keyboard toggle

On touch, Terminal ends in a dock shared by the phone browser, PWA and app. With the keyboard down, the tab row holds ‹ (Home), the tabs, +, All tabs (the tab list) and Show keyboard. With it up, the tab row stays, Show keyboard becoming Hide keyboard in the same place, and the compose box and the text-only key row sit under it. The web draws the controls; layout and sizes are in [browser-behaviors.md](browser-behaviors.md#phone-dock).

**Two targets share one keyboard.** The *terminal* target sends each keystroke as typed, from the terminal's own input (a text box in the page). The *line field* is an editable textarea, in the browser, the PWA and the app alike. Every text box carries the same keyboard settings (autocorrect, capitalization, spell checking and smart punctuation off); dictation may capitalize on its own. Nothing typed in the line target reaches tmux until Return.

| Action | Keyboard down | Terminal input owns it | Line field owns it |
| --- | --- | --- | --- |
| Keyboard toggle | terminal target takes it; keyboard up | keyboard down | keyboard down |
| Tap the line field | not shown | line target takes it; keyboard stays up | caret moves in the existing editor |
| Tap the terminal | terminal target takes it; keyboard up (a click in a mouse app: no change) | terminal stays selected (the prompt cursor moves on an input row) | terminal target takes it; keyboard stays up |
| Key-row unmodified ← / → | key row hidden | sent to the terminal | move the line caret |
| Key-row unmodified esc | key row hidden | sent to the terminal | terminal target takes focus; keyboard stays up |
| Key-row ↑, ↓, ^R, ^C, tab and other terminal controls | key row hidden | sent to the terminal | sent to the terminal |
| Key-row character key (`\| ~ / -`) | key row hidden | sent to the terminal | inserted at the caret |

Where a key-row key goes is one rule, `routeKey(key, owner, armed)` in `web/touch/keyRoute.ts`, the key row marks the keys it sends to the box. A caret step is the textarea's own, by grapheme, and waits while the keyboard composes. An armed ctrl or alt turns even ← and → into the chord for tmux.

The toggle, the box tap, the terminal tap and esc move DOM focus between the two boxes (`web/app/focus.ts`): Show keyboard focuses the terminal input, a box tap the line field, and Hide keyboard blurs whichever holds it. The box's terminal control also returns to terminal typing without hiding the keyboard.

**Focus cues** show which target owns the keyboard. Terminal: the terminal cursor is a solid block; the idle box has no caret and shows its draft or placeholder; Return is labelled Return. Line: the box has a ring, caret and Send, and the terminal cursor is a hollow outline. Return reads "return" in both: no field sets an `enterkeyhint`, so the keyboard's key is the system's plain one. The key row visually distinguishes keys that act on the box from keys that still go to tmux. There is one active typing cursor.

**Return** in the line field sends its text to the active tab and then Enter, and clears the field; the field keeps the keyboard for the next line. The text goes as one `paste` with `enter` (so a pane that asked for bracketed paste sees it delimited, with the Enter outside it); the daemon runs the Enter in the same tmux command group right after the paste, and tmux skips it if the paste fails. The daemon answers that paste exactly once, `pasted` or a refusal naming its `req` ([daemon-core.md](../daemon-core.md#53-json-messages)). A refusal puts the line back into that tab's draft, ahead of anything typed since, with the reason ("Not sent: …"); so does a socket drop before the answer, marked "May not have been sent". There is no client-side timeout: while the socket lives the daemon always answers, and a silent link ends in the socket's own idle close. A line is never resent automatically. Return with an empty field sends Enter alone. With the active tab not live, Return keeps the text and says "Not connected"; nothing is queued. Return captures the tab when pressed and never retargets.

**One line only.** A paste into the line field that holds a line break is not inserted: it goes to the terminal as one paste, without Enter, with a short notice. Multiline text therefore takes the same route as any terminal paste.

**Ctrl and alt** in the key row arm a modifier for the next key, from the key row, the terminal input or the line field; tapping it again disarms it. The armed modifier applies to the next single character typed outside IME composition, or the next key-row key, and sends the chord to the terminal, from the line field too, instead of inserting: `C-c` and `M-b` for a letter, a control byte for Ctrl on `[ \ ] ^ _ / ?`, and ESC then the character for Alt on punctuation, the rules of a hardware chord. A capital typed under an armed Ctrl still makes Ctrl-C (a hardware Ctrl+Shift+letter is `C-C`, as a hardware keyboard sends it). A composition starting, or a multi-character insert (swipe typing, a prediction), disarms it and goes through unmodified. Locking is not built.

**The unsent line is a draft.** Each tab key has its own draft, so switching tabs swaps the field's text and Return can only send a line to the tab it was written for. The draft survives keyboard hide, blur, navigation and reload on the same device. Persistence is per stable target identity, bounded, and local only; no sync or upload before Return. Saving text is not encryption: browser-origin script can read it and browser storage can be cleared, evicted or unavailable. Show storage failure rather than silently promise persistence. Clear local data removes drafts. A closed tab's draft is kept and returns when that session is opened again. At most 32 drafts: past that, the least recently edited draft of a session with no open tab goes, and if every one belongs to an open tab a new draft is refused.

**The toggle's state** comes from focus, not geometry: in the browser, from `focusin` and `focusout` on the two inputs, so Safari's Done or ⌃ ⌄ keep it right; if the keyboard geometry drops while an input still holds focus, the input is blurred and the state is "down". It therefore still works with a hardware keyboard attached, which never raises the on-screen keyboard. In the browser, one bubble-phase keydown listener on the document (`Terminals.hardwareKey`, the rule is `routeHardwareKey`) sends hardware keys to tmux that do not type text: the terminal input sends every chord, Escape, Tab and arrow; the line box only Control chords, Escape, Tab, ↑ and ↓ (the rest edit its text). With no box focused it sends those and also types: a single character, Enter and Backspace go to the terminal on screen. It runs after the page's own handlers and skips a key already claimed (`defaultPrevented` or stopped), so the line box's Enter and an open menu's Escape keep theirs. Another focused field, an open dialog and an IME composing keep their keys. A tab menu is not modal, so apart from its Escape the keys typed while it is open go to the terminal, as they do with the keyboard up; and Tab with no box focused goes to tmux rather than moving focus into the page, since on a phone the terminal is what a hardware keyboard types into.

**Keyboard visibility** is not focus alone: hardware keyboards and Safari chrome or zoom complicate `visualViewport` height. Use `visualViewport` resize and scroll with focus, exclude zoom changes, and verify on real iOS. Native reports keyboard geometry from the keyboard lifecycle. No guessed fixed keyboard height and no polling.

## Options and rejected shortcuts

- Rely on xterm's default desktop selection on iPhone: upstream issues and pinned implementation do not justify it.
- Make a WebGL canvas selectable with user-select:text: it creates no text. Desktop keeps WebGL and xterm's own selection; the phone draws DOM rows instead.
- Reconstruct wrap by row length: confuses full-width hard breaks with soft wraps; fails with Unicode/padding.
- Call clipboard.readText on every tap: conflicts with platform activation/permission model and user intent.
- Route line-field input events straight to the terminal while composing: breaks IME replacement, and the line field exists to edit before sending.
- A multiline draft editor with an Insert button that sends without Enter: replaced by the line field (Jimmy: "edit should be a single line editor").
- Resize tmux on every keyboard frame: violates existing no-resize-on-keyboard contract, causes redraws and copy instability.

## Why these choices

- **The terminal's rows are muxen's, not xterm's.** The row list draws the model's frames with its own run-based rows, so rows stay put under scrolling and a selection. A native scroller over xterm's DOM renderer ends any selection, because that renderer redraws rows in place. JS momentum over xterm's buffer needed a second scroll position and a patch per seam. tmux copy-mode was ruled out because every scroll would change the pane's state, and tmux's own state is what muxen must not disturb. Desktop moves to the same list, so there is one implementation everywhere; until then desktop is drawn by xterm and finger scrolling is gone there (the wheel and trackpad work).
- **A selection survives scrolling and autoscrolls at the list's edges**, which needs a scroller the selection lives in. Typing while scrolled up jumps to the latest row so the typed text shows. After output overflows, the list keeps its rows under an "output skipped" row and fetches nothing more until the next snapshot. A tap on a URL on touch does nothing: copy and paste are the way ([issue 4](https://github.com/haowjy/muxen/issues/4) holds opening links as an experiment).
- **The selection follows text that moved.** Measured on real Claude Code 2.1.316 and OpenCode 2.2.5 traffic, fullscreen apps repaint completed paragraphs one to three rows up or down in place. Closing the selection on any rewrite closed all 12 sampled selections 1.7 to 2.7 s after they were made; following the moved block kept 17 of 18 for 10 s, against 6 of 18. Following characters rather than rows was ruled out because it needs partial-row matching. muxen does not honor synchronized output (`CSI ? 2026`), so a repaint that reaches the model as two frames (erase, then text) closes the selection.
- **The long press selects at once, and there is no arrow pad.** The pad drew nothing, so a press meant to select looked dead once the finger moved past 16 px. ← and → are keys that repeat while held. A tap on the cursor's row or the row above or below raises the keyboard, so typing where the cursor is needs no trip to the toggle.
- **In the app the hold is muxen's mark in both keyboard states.** iOS's own long-press selection with the keyboard down felt slow, and two selections would have two looks and two lifetimes. The mark draws boxes in the scroller's content coordinates; the rows are `user-select: none` where the platform has an edit menu, because WebKit paints no CSS Custom Highlight on such text and would take the touch. A browser has no edit menu and keeps WebKit's selection. One `Selection` interface is picked once at construction, so every rule about the selection is written once.
- **The edit menu is native's**, presented over the page's mark. A menu the web draws moves the selection or the keyboard when touched and doesn't match the system's. Native owns whether it is up, because iOS can dismiss it itself and a page that tracked it went stale.
- **The touch shell counts the fingers the platform lists, not the ends it was sent.** On the iPhone a touch that began on a row xterm then replaced was dispatched to a detached node, so no end reached the surface, and the leaked finger made every later swipe a two-finger one that the recognizer ignores. A timeout on a counted finger was ruled out: a held finger is long and legitimate.
- **No Paste button in the dock.** The resting row has room for the tab button, the field and the toggle only, and the edit menu is where iOS users look for Paste on content that isn't a text field.
- **The keyboard pan keeps the terminal's last row visible** unless that would hide the cursor. Full-screen harnesses park the cursor above their input and status rows, so cursor-only anchoring hides those rows; bottom-only anchoring can push a cursor near the top off screen. Resizing tmux to the visible rows with the keyboard up was ruled out: each toggle would redraw every TUI over a spotty link and resize the laptop's view.
- **The app has no native text input.** The page's own boxes hold the keyboard, as in Safari. The earlier hidden native field mirrored into the web dock made a late `lineSet` reply overwrite the box mid-typing and needed a second tap to open the keyboard.
